# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Doctylia — a multi-tenant SaaS platform giving doctors their own branded booking website plus a practice-management admin panel (appointments, patients, billing, staff), on top of a Supabase backend. Vite + React + TypeScript + Tailwind CSS + shadcn/ui (Radix) on the frontend.

This project is synced with [Lovable](https://lovable.dev): pushes to `main` sync back into the Lovable editor, and prompts run there commit straight back to this repo. Don't assume a change here is the only place that history lives.

## Commands

```sh
npm run dev          # start Vite dev server (port 8080, see vite.config.ts)
npm run build         # production build
npm run build:dev     # development-mode build
npm run lint           # eslint .
npm run preview        # preview a production build
npm run test            # vitest run (single run, all tests)
npm run test:watch      # vitest in watch mode
npx vitest run path/to/file.test.tsx        # run a single test file
npx vitest run -t "test name"               # run tests matching a name
npx tsc --noEmit -p .                        # typecheck without emitting
```

Tests live colocated next to the source they cover (e.g. `src/lib/planFeatures.ts` + `src/lib/planFeatures.test.ts`), run under jsdom via `src/test/setup.ts`. `@testing-library/react` is used throughout.

**Radix Tabs gotcha**: Radix `Tabs` use `activationMode="automatic"`, which activates on focus, not click. In tests, call `.focus()` on the tab trigger before `fireEvent.click()`, or the click won't register.

## Architecture

### Four app surfaces, one route tree

`src/App.tsx` is the single router covering four distinct UIs:

- **Public marketing site** (`/`) — `src/pages/LandingPage.tsx` composing `src/components/landing/*`.
- **Doctor's public booking site** (`/dr/:slug`, plus `/dr/:slug/blog`, `/dr/:slug/manage`) — `src/pages/DoctorPublicPage.tsx` composing `src/components/doctor/*`, all reading from `DoctorContext` (see below).
- **Doctor/staff admin panel** (`/admin/*`, behind `ProtectedRoute`) — `src/pages/AdminDashboard.tsx` is a nested router inside `AdminLayout`; every page is lazy-loaded and wrapped in `PermissionGate` (see permissions below). Components live in `src/components/admin/*`.
- **Platform superadmin panel** (`/superadmin/*`, behind `SuperAdminRoute`) — nested routes defined directly in `App.tsx`, layout in `SuperAdminLayout`, pages in `src/components/superadmin/*` (prefixed `SA*`).

`src/components/shared/*` and `src/components/ui/*` (shadcn primitives) are used across surfaces.

### Two separate role/permission systems — don't conflate them

1. **Platform-level** (superadmin panel access): a `user_roles` table with roles like `"admin"`. `SuperAdminRoute` checks it via the `has_role` Postgres RPC, not via the `profiles` table.
2. **Practice-level** (admin panel access): a doctor has a `profiles` row; a staff member they've invited has a `staff_members` row instead (no `profiles` row of their own — `handle_new_user()` deliberately skips creating one for staff). `useProfile()` (`src/hooks/useProfile.ts`) resolves either identity, and when the caller is staff it returns the **assigned doctor's** profile so `.eq("doctor_id", profile.id)`-style queries work unchanged for both actors — actual read/write authorization is enforced per-table by Postgres RLS, not by this client-side resolution.

Staff permissions are fine-grained keys like `"patients.view"` / `"billing.manage"`, defined in `src/lib/staffPermissions.ts` and gated twice: the admin sidebar hides links a staff member can't use, and each route in `AdminDashboard.tsx` is separately wrapped in `<PermissionGate permission="...">` so a manually-typed URL is still blocked. **`src/lib/staffPermissions.ts` must be kept in sync by hand with `supabase/functions/_shared/staffPermissions.ts`** — edge functions run on Deno and can't import from `src/`, so the permission keys are duplicated rather than shared.

**Superadmin Team** (`/superadmin/team`, owner-only): permission-scoped platform admins who log in from the main login page with phone + OTP. They live only in `superadmin_team_members` (never `user_roles` 'admin', which means full owner access) and get access through additive `sa_has_permission(...)` RLS policies and `hasSuperadminPermission` checks in edge functions. **`src/lib/superadminPermissions.ts` must be kept in sync by hand with `supabase/functions/_shared/superadminPermissions.ts` and the policies in the `superadmin_team` migration.** Post-login routing for all four actor types (owner, team, clinic staff, doctor) lives in `src/lib/auth/resolveDestination.ts`.

### Supabase integration

- `src/integrations/supabase/client.ts` and `types.ts` are **auto-generated** — don't hand-edit; regenerate via the Supabase MCP/CLI instead.
- Edge functions live in `supabase/functions/*` (Deno runtime), one directory per function; `supabase/functions/_shared/` holds code duplicated between client and functions (see permissions note above).
- `supabase/functions/mcp/` is **hand-maintained and must never be regenerated**, in dev or in a build — the `mcpPlugin`/`componentTagger` sync mishandles absolute paths on Windows (see the comment in `vite.config.ts`). It's excluded from dev-server file watching for the same reason.
- Payments run through Razorpay (`create-razorpay-order`, `verify-razorpay-payment`, `razorpay-webhook`, refunds, payouts) — in addition to doctor subscription plans, online patient payments for consultations and clinical services deduct the configured platform service charge percentage (`profiles.commission_percent` override or `platform_settings.default_commission_percent`) and automatically route the net doctor share (`doctor_share`) to the doctor's Razorpay Route Linked Account (`transfers[]` on order creation, reversed via `reverse_all: 1` on refund). See `CONTEXT.md` and `docs/adr/0001-razorpay-route-commission-split.md`.
- Migrations are in `supabase/migrations/` (sequential, timestamped) — this is the source of truth for schema, not the generated `types.ts`.

### Appointments, patients and the live queue

The database owns these rules; the UI only calls and renders them (`supabase/migrations/20261029*.sql`):

- **Patient record + visit count + invoice** are produced by `BEFORE`/`AFTER` triggers on `appointments` (`sync_appointment_patient`, `invoice_on_appointment_billable`), not by client code. Staff bookings create the patient immediately; the visit is counted once (`visit_counted`) when the appointment becomes completed; an invoice exists only once the visit is completed **and** paid (or pay-at-clinic).
- **Patient lifecycle** (`20261029120000_patient_lifecycle.sql`): a staff booking creates a *provisional* patient (`patients.auto_created`, zero visits). Cancel / no-show / delete releases it again via `release_provisional_patient()` unless the patient has notes, another live or completed appointment, or any row in any table referencing `patients` (checked from the catalog). A visit counts only while its appointment is `completed`; leaving that status un-counts it. Manually added patients are never auto-deleted.
- **Patient CSV import/export** (`src/lib/patientCsv.ts`, `patientImport.ts`, `PatientImportDialog.tsx`): import reads Name, Phone, Age, Gender (required) plus Email, Weight (kg), Notes with the same validators as the Add Patient form; header names are matched loosely and unknown columns are ignored. Optional history columns Patient Since, First Visit, Last Visit and Total Visits (DD/MM/YYYY, real dates, not in the future; First Visit doubles as Patient Since) keep a long-standing patient's real dates: `patients.patient_since` (separate from `created_at`, which stays the day it was added here) plus `first_visit` / `last_visit` / `total_visits`, which later completed appointments then add to. Medical history and reports are deliberately NOT imported; they are added per patient afterwards. Rows matching an existing patient (phone + lower-cased name, the `uq_patients_doctor_phone_name` key) or repeated in the file are skipped, never overwritten. Export is built by `patientsToCsv` from the same module so an export re-imports cleanly (a test enforces the round trip). Limits: 1000 rows and 2 MB per file in the browser; the real enforcement is in the database. Import is **Pro/Premium only** (`plan_status = 'active'` and `plan_end` not passed; free, trial, expired and cancelled clinics are refused) and the browser calls the single `import_patients(rows jsonb, file_name text)` function (clinic taken from `auth.uid()`: the doctor, or active staff with `patients.add`; never from the payload). It is all-or-nothing, validates every row again in SQL (reject codes `NAME`, `PHONE`, ...), skips duplicates, and refuses with `NOT_ELIGIBLE`, `PAYLOAD_INVALID`, `DAILY_LIMIT` (5 imports and 2,000 rows per 24 h) or `CAP_EXCEEDED` (Pro 2,000 / Premium 10,000 patients held when the import runs; duplicates and bookings do not count). All numbers live in `platform_settings` (`patient_import_*`). A trigger on `patients` (`trg_a0_guard_patient_direct_inserts`) throttles every client-made insert per clinic and can never be skipped by a signed-in user: direct adds are limited to 100/hour and 300/day (`PATIENT_RATE_LIMIT`) and refused once the clinic holds `patient_import_cap_ceiling` (100,000) patients (`PATIENT_TOTAL_LIMIT`); patients auto-created by the appointment triggers (depth > 1) count against a separate 1,500/day booking counter. Exempt: `import_patients` (transaction-local `app.patient_import` flag) and calls with no JWT (service role, cron, migrations). The guard resolves the caller's clinic and ignores a `doctor_id` that is not theirs, so RLS rejects it without touching another clinic's counters. The import log stores only the file extension, never the file name (names can contain patient names). Superadmins cannot review their own clinic's request or override. A clinic needing more requests a higher limit (`patient_import_requests`, one open request, 7-day wait after a decline); superadmin decides on the Plan Requests "Import limits" tab (reuses `plan_requests.view/manage`; approving a clinic that is not eligible is refused), and can allow or block one clinic through `patient_import_overrides` (card on the doctor detail page; a table of its own so the doctor cannot edit it). `get_patient_import_access()` only feeds the UI. Database checks live in `supabase/tests/patient-import/*.sql` and run with `npx supabase db query --linked -f <file>` (each rolls back and prints one `pass` row).
- **Patient documents** (`DocumentsTab`, rules in `src/lib/patientDocuments.ts`): up to 20 files per batch, 10 MB each (the private `patient-documents` bucket enforces the same size and PDF/JPEG/PNG/WebP types server-side), real type checked from the file's first bytes, large photos shrunk to JPEG in the browser, camera capture button, type suggested from the file name and date from the file's own date. Bulk cross-patient document import was deliberately left out.
- **Queue columns are RPC-only** (`20261029140000_review_hardening.sql`): `queue_number`, `priority(_reason)`, `serving_started_at`, `skipped_at`, `sort_time` and `created_at` cannot be written directly by clients (`QUEUE_FIELDS_LOCKED`); only `queue_action` can (it sets the transaction-local `app.queue_rpc` flag the guard checks). `call_next` / `call` take `_expect` (`'none'` or the appointment id the screen thinks is in the room) and answer `STALE` if another device changed it. Public bookings must carry a `time_slot` and are stamped with the server's `created_at`.
- **Lock order** is slot -> queue number -> patient. That is why the slot triggers are named `trg_a0_*` (triggers fire alphabetically); keep new triggers that take advisory locks in that order.
- **Abuse limits & billing rules** (`20261029150000_abuse_limits_and_billing_rules.sql`): token lookups (`get_appointment_by_token`, cancel, reschedule, `get_my_queue_status`) lock a clinic+phone pair for 15 minutes after 8 failed guesses (`token_lookup_attempts`); a public booking needs a real phone, at most 3 open future bookings per phone and clinic, and its `amount` is overwritten from the clinic's own services (`public_booking_price`). **An invoice is created only when the appointment is completed AND `payment_status = 'paid'`**, so the UI asks how the patient paid when completing an unpaid visit (queue and appointments list). Online-paid no-shows are marked `no_show` and the doctor gets a `paid_no_show` notification; nothing is refunded automatically. `mark_paid` deliberately needs only `appointments.edit` (counter staff do it all day, and the guard already lets them set `paid` directly), and every call is logged in `queue_events`.
- **Type-checking**: the root `tsconfig.json` has no `files`, so `npx tsc --noEmit -p .` checks nothing. Use `npx tsc --noEmit -p tsconfig.app.json` (two old errors remain in `SADoctorDetail.tsx` and `NotFound.tsx`).
- **Booking tokens** (`src/lib/bookingToken.ts`, mirrored in `verify-razorpay-payment`) are 7 random characters from a 31-letter alphabet. Older `T123`-style tokens still work for lookups.
- **`guard_appointment_writes`** forces anonymous bookings to `pending` / `pay_at_clinic` and blocks client writes to gateway payment columns and to `refunded`. Edge functions use the service role and are trusted; cron and migrations have no JWT role and are trusted too.
- **Payment mode & references** (`20261118100000_payment_details_and_vitals.sql`): a counter payment records `payment_method` (cash/upi/card); UPI needs a 12-digit UTR and card an approval code / last 4 digits in `appointments.payment_reference`, enforced by the `trg_a1c_payment_reference` trigger (clinic writes only; edge functions and cron are exempt) and a unique index so one UTR backs one payment per doctor. `queue_action` is now a thin wrapper (6 args, adds `_payment_reference`) around `queue_action_core`, which keeps the old logic. `ensure_invoice_for_appointment` copies method + reference onto `invoices` (`online` for Razorpay) so Billing can split revenue by mode. Rules live in `src/lib/paymentDetails.ts`; patient age/gender/weight rules in `src/lib/patientIntake.ts`, shared by the Add Appointment and Add Patient forms. Age and gender are required there, weight is optional, and `trg_a6_sync_patient_vitals` copies them onto the patient record.
- **Queue**: `appointments.queue_number` is assigned by the database per doctor per day (never by the browser). Staff actions go through the single `queue_action` RPC (call next, complete, skip, recall, no-show, priority with a required reason, mark paid) and are logged to `queue_events`. Waiting order is `priority DESC, sort_time, created_at`; `src/lib/queue.ts` mirrors it for rendering. Public screens (`/dr/:slug/queue`, the manage-appointment page) use `get_public_queue` / `get_my_queue_status`, which return queue **numbers only** — never phones or complaints. The one exception: `get_public_queue` also returns `now_serving_name`, the patient currently in the room as a name masked in SQL (first name + last initial, e.g. "Aaryan K."); waiting and finished patients are never named.
- Overdue appointments are closed nightly by `expire_overdue_appointments()` (called-but-unclosed → completed, never-called → no-show); the browser no longer does this.

### Multi-doctor clinics (practitioners)

Spec: `docs/superpowers/specs/2026-11-25-multi-doctor-clinic-design.md`.
- **Tenant and doctors:** `doctor_id` is still the clinic tenant everywhere. `practitioners` are the doctors who see patients there; each clinic has exactly one `is_primary` (the owner by default, created by `ensure_primary_practitioner`).
- **Which rows carry `practitioner_id`:** `appointments`, `working_hours`, `prescriptions`, `patient_visits` (NOT NULL) and `patient_documents` (nullable). Patients, medical history, invoices and services stay clinic-level.
- **`trg_a00_fill_practitioner`:** fills a missing value only when it is unambiguous (single doctor, or the caller / visit / appointment says who). Otherwise it raises `PRACTITIONER_REQUIRED`. **New code for multi-doctor flows must always send `practitioner_id`.** Composite FKs `(practitioner_id, doctor_id)` keep it inside the clinic.
- **Per-doctor scope:** slots, queue numbers, "in the room", `queue_action` locks, `get_slot_counts` / `get_public_queue` and `get_my_queue_status` are per practitioner. Any slot lock must use `slot_lock_key()`.
- **RPC defaults and same-day moves:** a NULL `_practitioner_id` means the primary. A same-day change of doctor must go through `queue_action('transfer')` (`USE_QUEUE_TRANSFER`).
- `appointments.sort_time` is an IST `time` recomputed by `trg_set_appointment_sort_time` whenever `time_slot` is in an UPDATE's SET list; set `sort_time` in a separate UPDATE (see `queue_action` transfer).
- `get_slot_counts` returns `time_slot` as text from a `time` column (`'10:00:00'`); compare with `::time` in SQL tests.
- **Entitlements and the launch gate:** `clinic_multi_doctor_enabled()` (feature `multi_doctor` + `platform_settings.multi_doctor_enabled` or a per-clinic override), `clinic_doctor_seat_limit()` (1 + `clinic_doctor_seats.extra_seats`, +1 in trial, capped by `doctor_seat_max`) and `practitioner_within_seats()` (main doctor first, then `sort_order`). A doctor outside the seats keeps every booking but takes no new ones; bookings and the booking auto-pick only use doctors within seats. `doctor_seat_price` is unset on purpose (no purchase flow yet).
- **A clinic with 2+ ACTIVE practitioners is multi-doctor whatever its plan** (`usePractitioners().isMulti`); the plan only decides whether it can ADD or re-enable doctors. Doctor writes go through RPCs only (`upsert_practitioner`, `set_practitioner_status`, `set_primary_practitioner`, `reassign_practitioner_appointments`); there is no client write policy on `practitioners`.
- **Doctor logins** are `staff_members` rows with `role = 'doctor'` + `practitioner_id`; only the clinic owner may create, change, delete or change the phone of one (trigger `trg_guard_doctor_role_staff` for table writes, and explicit owner checks in `create-staff-account` / `delete-staff-account` / `update-staff-phone`, because edge functions run as service role). `PERMISSION_PRESETS.doctor` deliberately has no `appointments.create`: doctor logins do not book, reception does.
- **Clinical visibility** (`website_settings.clinical_visibility`, owner-only): `shared` or `treating`. RESTRICTIVE policies only bite for doctor logins (`clinical_row_visible`). `appointments.all_doctors` is enforced for queue actions, but viewing appointments is a convenience filter, not a privacy boundary. `clinical_access_log` is a client-called 'record opened' log, NOT an audit trail: the database cannot log reads that bypass the app. `website_settings` is publicly readable, so the visibility mode is not secret.
- **Paid online bookings** carry the chosen doctor: `create-razorpay-order` resolves it with `_shared/practitioners.ts` (`pickBookingPractitioner`, within seats and `online_booking`, doctor's own fee, per-doctor slot check) and `verify-razorpay-payment` inserts with it; a paid booking is never refused for seat/bookable changes after payment (service role skips those checks), and a refusal returns `refund_pending` + the payment id.
- **Fail closed:** `staff_doctor_id()` / `staff_has_permission()` are NULL for strangers, so `IF NOT (a OR b)` skips the refusal. Wrap every permission OR-chain in plpgsql in `COALESCE(..., false)`, and give every RPC a 'stranger is refused' test. Test clinics with two bookable doctors need a pilot override (`doctor_feature_overrides`, `granted_by` set) plus seats or a trial.
- **Shared slip names:** `get_shared_prescription` and `src/lib/practitioners/slipDoctor.ts` must strip a leading 'Dr.'/'Dr ' from a doctor's name the same way (never 'Drake') and use the same clinic-name fallback.
- **Seat purchase** (Premium + active plan + real `plan_end` only; never trial): seats are DATED PERIODS in `clinic_seat_periods`, and `clinic_doctor_seat_limit()` = 1 + superadmin-granted `clinic_doctor_seats.extra_seats` + the periods active now (+ trial seat), capped by `doctor_seat_max`, so a late cron can never grant free seats. A seat order is priced ONLY in SQL (`seat_order_quote`: `ceil(qty × price × charged_days/30)`, `charged_days ≤ 30`, period ends at the earlier of 30 days and `plan_end`; `get_seat_order_quote` for the UI, `seat_order_quote` is service-role only) and goes through `create-doctor-seat-order` → Razorpay → `verify-plan-upgrade-payment` → `apply_plan_upgrade_payment` (same locked idempotent path as plan payments; a renewal order may carry `seats`, checked up front by `renewal_seats_check`). `doctor_seat_price` unset = purchase refused/hidden. A payment that was taken but could not be applied is parked as `plan_upgrade_payments.needs_refund` (+ reason, owner notification, superadmin badge) and EVERY replay keeps reporting `not_applied`; verify returns HTTP 200 `{ok:false, needs_refund:true, code, payment_id}` for it, so clients must read the body. Refunding a payment (any path) deletes its seat periods (trigger). Seats are non-refundable by policy; superadmin can still grant seats.
- **Per-doctor revenue** is computed in SQL (`get_practitioner_revenue` for the owner/`billing.view`, `get_my_practitioner_revenue` for a doctor login, only when the owner turned on `website_settings.show_doctor_earnings`). The doctor is snapshotted on the invoice (`invoices.practitioner_id`, trigger; `ensure_invoice_for_appointment` is untouched), so later transfers/deletions don't move money. Revenue is AS INVOICED (ex-GST; a later refund does not rewrite the month), refunds are listed in the month they were made, paid online no-shows are their own bucket, dates are IST.
- **Doctor-aware content:** `service_practitioners` (no rows = every active doctor offers the service; rows for inactive doctors are ignored; enforced by `public_booking_price`, `SERVICE_NOT_OFFERED` on the anon pay-at-clinic insert and `INVALID_SERVICE` in `create-razorpay-order`, never after payment), nullable `reviews.practitioner_id` / `blog_posts.practitioner_id` (NULL = the clinic; the reviews trigger forces `is_verified/is_pinned = false` for the public and caps length/rate), per-doctor directory rows only for clinics with 2+ active doctors (`directory_entries_v`), `practitioners.directory_listed` honoured by the sitemap and `noindex` on the doctor page. Blog JSON-LD authors become the doctor only when the post has a practitioner AND the clinic has 2+ active doctors.
- **Launch controls:** the superadmin 'Multiple doctors' card (Flags page) saves through `set_multi_doctor_settings` (validated, all-or-nothing); a trigger audits every change to `multi_doctor_enabled`, `doctor_seat_price`, `doctor_seat_max`, `trial_extra_doctor_seats`. `clinical_access_log` rows older than 1 year are purged daily (pg_cron `purge-clinical-access-log`).
- **Who is the main doctor:** exactly one `is_primary` per clinic (the owner by default). It is the fallback for anything that names no doctor (backfilled rows, RPCs with NULL `_practitioner_id`), it mirrors the owner's profile (name/photo/registration edited in Settings, not the Doctors list), sorts first on the public site, and can never be deactivated or stopped from bookings (`set_primary_practitioner` moves it). It grants no extra permissions.
- **Prescribing doctor is explicit:** owner and reception pick it on `PrescriptionsPage` (defaulted from the patient's last non-cancelled appointment, then last visit); only a doctor login (`role === 'doctor'`) writes as themselves. The owner is also a practitioner, so never infer "no pick needed" from `myPractitionerId` alone. VisitsTab follows the same rule.
- **Patients by doctor:** `patients_with_doctors` is a `security_invoker` view (patients columns + `practitioner_ids`, `last_practitioner_id` from non-cancelled appointments, live visits and prescriptions). The Patients page, dashboard and patient header use it in multi-doctor clinics. The patient LIST is deliberately clinic-wide even in 'treating' mode (a doctor must find a walk-in patient; otherwise duplicates); only visits, prescriptions and documents are restricted.
- **Doctor logins and money:** `get_practitioner_revenue` returns `DOCTOR_LOGIN` for any `role='doctor'` login; their own figures come from `get_my_practitioner_revenue` (owner opt-in). RESTRICTIVE policies via `invoice_row_visible` let a doctor login see/change only invoices with their own `practitioner_id`. The Revenue page shows a "Doctor earnings" strip at the top plus a Doctor filter that narrows the whole page (strip = as-invoiced; cards = excl. refunded, per-period: the banner explains the difference).
- **Editing a doctor login's permissions:** owner only, from Staff Management (row → "Permissions") or the Doctors page ("Permissions" link, `/admin/staff?edit=<login id>`). Only `permissions` is written; name follows the doctor and phone changes stay on the Doctors page. The doctor preset is the starting point, not a ceiling.
- **Doctor self-edit:** a doctor login edits only its OWN bio, photo and signature through `update_my_practitioner_profile` (NULL keeps, `''` clears; bio <= 2000 chars; URLs must be that doctor's own `doctor-uploads/<clinic>/practitioners/<own id>/(photo|signature).<ext>`), UI in `MyDoctorDetailsCard` (Settings, doctor logins only; they never see the owner's clinic profile). A storage exception (`own_practitioner_upload_path`) lets them upload exactly those two files; everything else on a practitioner stays owner-only (`upsert_practitioner`). Because the bio is now doctor-written, render it as plain text everywhere (React text nodes / escaped in Edge HTML and JSON-LD).
- **Known and accepted:** appointment rows (names, amounts, status) of other doctors are readable by a doctor login through the API (viewing is a convenience filter, not a privacy boundary); invoices and the revenue report are the money boundary. Reminders name the treating doctor in 2+ doctor clinics (`_shared/checkupDoctor.ts`, falls back to the owner on any gap).
- **Deleting a clinic:** `prescriptions.doctor_id` has no FK to profiles, so trigger `trg_a0_delete_clinic_prescriptions` (BEFORE DELETE on profiles) removes the clinic's prescriptions; otherwise `prescriptions_practitioner_fk` blocks the cascade to `practitioners`. Any new table with a composite FK to `practitioners` needs a cascade path from `profiles` too.
- **RLS performance:** policies on large tables must wrap `auth.uid()`, `has_role`, `sa_has_permission`, `staff_*` in a scalar sub-select (`(SELECT auth.uid())`), as `20261127140000_rls_initplan_patient_reads.sql` did for patients/appointments/patient_visits/prescriptions (5,000-patient clinic: 4.7 s -> 0.23 s). Realtime publication only includes `appointments` among the patient tables; others refresh on reload/tab focus (deliberate).
- **Deno:** `npx -y deno check supabase/functions/<fn>/index.ts` works from the repo root (no install needed). `refund-payment`, `admin-delete-doctors` and the other functions that call `hasSuperadminPermission(admin, …)` have an old typing mismatch in that helper; deploys don't type-check, so it is not a blocker.
- **Checks:** run `supabase/tests/multi-doctor/*.sql`.

### Prescription sharing

Manual only, never automatic. `PrescriptionShare` (in the slip's action bar) calls `create_prescription_share`, which makes one active link per prescription (30 days, earlier links revoked; only the SHA-256 is stored, the token is returned once) and opens `wa.me/<patient phone>` with the link. The patient opens `/rx/:token` (`SharedPrescription`, noindex) and must enter the last 4 digits of the phone saved on the patient record; `get_shared_prescription` locks a link for 15 minutes after 8 wrong guesses (reuses `token_lookup_attempts`, key `rx:<share id>`). Sharing needs `prescriptions.view`. `prescription_shares` is read-only to clients (writes via the RPCs); the slip body is the shared `PrescriptionSlipCard`.

### Prescription templates

Spec: `docs/superpowers/specs/2026-11-27-prescription-templates-design.md`. Doctors build their own slip layout and extra fields (e.g. a dental case sheet with OPD no., tooth chart, pain scale) from **Prescriptions → Templates**.
- **A template is an ordered list of blocks plus look settings** (`TemplateConfig` v1, `src/lib/prescriptionTemplate/types.ts`): built-in blocks `patient_info` (a checklist of info rows; `diagnosis`/`complaint`/`symptoms` live there), `vitals`, `medicines`, `advice`, `follow_up`, `signature`, and any number of `custom` blocks (text, textarea, number, select, multiselect, checkbox, date, `tooth_chart` (FDI numbering, one status per tooth), `pain_scale`). Look settings: accent `#rrggbb`, title, header/footer toggles, `letterhead: 'preprinted'` (blank spacers for the clinic's own stationery).
- **The built-in default (`defaultTemplateConfig`) is a frozen contract**: it reproduces the slip as it was before templates, and a prescription with no `template_snapshot` renders with it. Never change it casually; version the config instead.
- **Storage**: `prescription_templates` (clinic-wide when `practitioner_id` is NULL, otherwise one doctor's; one default per scope and max 20 per clinic, both by trigger), `prescriptions.extra` (answers keyed by block id), `prescriptions.template_snapshot` (the layout at issue time, so editing a template never changes old slips) and `template_id` (informational, `ON DELETE SET NULL`). `prescription_template_config_valid()` checks shape and limits in SQL; `src/lib/prescriptionTemplate/config.ts` (`parseTemplateConfig`, tolerant; `validateTemplateConfig`, for the builder) mirrors it: keep the limits in sync.
- **Carry forward**: a custom field with `carryForward` (on for histories and allergies in the Dental preset) is pre-filled in a New prescription from the patient's last prescription (`carryForwardValues`: matched by block id, then by same name and type; only empty fields, never overwriting typed answers). Once any answer is typed, a change of prescribing doctor no longer auto-switches the template (it would drop the answers). The accent must have at least 3:1 contrast on white (`contrastOnWhite`), or the printed header and QR code become unreadable.
- **Built-in rows are filled on the prescription itself** (spec addendum 2026-11-28): complaint, symptoms and vitals are typed in the form and stored in `prescriptions.extra` under reserved `sys_` keys (`sys_complaint`, `sys_symptoms`, `sys_vital_<key>`; custom block ids may not start with `sys_`). The slip prefers them and falls back to the linked visit, so older prescriptions are unchanged. `vitals` and `advice` blocks carry `fields` (which vitals / kinds of advice the template offers; a block without `fields`, e.g. an old snapshot, parses to the defaults that reproduce the old slip) and a custom field has a `placement` (`section` | `patient_info` | `vitals` | `advice`, only for field types that fit). A placed field is only offered while its host section is on (`isOffered`): off means not asked for, validated, carried forward, saved or printed. No migration was needed because the SQL validator ignores these keys; keep it that way (never tighten it in place). Vitals rules live in `vitals.ts` (temperature is always °F: a Celsius-looking value is refused; BP is `sys/dia`; BMI is computed from height and weight).
- **Auto-fill safety** (`PrescriptionsPage`): complaint, symptoms and vitals start from the patient's visit of the prescription's date (this doctor's, in a multi-doctor clinic) and carry-forward fields from the last prescription. Both are patient-specific, so changing to another patient removes them AND the typed complaint, symptoms, vitals and carry-forward answers (a first pick keeps what was typed); changing the date drops the unedited visit values. Values filled automatically do not count as typed when deciding whether a change of doctor may switch the template. A template the doctor just created is the default (the previous default stays in the Template box); the form says which layout it is using.
- **Who edits**: the owner edits every template; a doctor login (`prescriptions.edit`) only templates scoped to its own practitioner (RLS + `canEdit` in `PrescriptionTemplatesDialog`); everyone who can view/create prescriptions can read them. No new permission key.
- **One renderer**: `PrescriptionSlipCard` (`template` prop > `prescription.template_snapshot` > default) serves the preview, print, PDF and `/rx/:token`; `get_shared_prescription` also returns `extra` and `template_snapshot`. The PDF pipeline selectors (`data-prescription-slip-header|body|footer|row`) are unchanged; in pre-printed mode header/footer stay in the DOM as blank spacers, and a footer with nothing to show is not rendered at all (a zero-size element would break the PDF maths). Pre-printed spacers are sized by width ratio (`A4_CONTENT_MM`), not mm, because the PDF scales by element width; the patient's `/rx` page passes `forceLetterhead` so the patient still sees the clinic header. Known limit: on a multi-page browser **Print** the pre-printed footer space is only reserved at the end of the slip (the PDF pins it on every page).
- **Writes stay backward compatible**: `PrescriptionsPage` only sends `extra`, `template_id`, `template_snapshot` and the advice/follow-up columns when they carry data, a section the template switched off is never written, and a failed template load means "no templates".
- **Migrations** `20261127190000` (+ `190100`, which only validates the NOT VALID constraints in its own transaction) are applied. Never tighten `prescription_template_config_valid()` in place (CHECKs re-run on every update): add a `_v2`.
- **Checks**: `supabase/tests/prescription-templates/01_templates.sql` (rolled back, prints `pass`).

### Custom plans (Plan Requests)

A custom plan (`doctor_custom_plans`) is a feature set plus a monthly price negotiated on top of **one** paid tier (`base_tier`). It changes a doctor's price and features **only while `profiles.plan_tier = base_tier`**: the pricing cards (`getDoctorTierPrice`), the checkout (`create-plan-upgrade-order`) and `doctor_active_custom_plan()` all apply that same rule, and `customPlanApplication()` in `src/lib/customPlan.ts` is its client form (`applies` / `tier_mismatch` / `none`). `20261029160000_custom_plan_integrity.sql` keeps this honest: requests and approvals need a Pro/Premium doctor, a `plan_tier` change ends a plan built on the old tier (event + notification), and `rebase_custom_plan()` (superadmin button "Apply to <tier>") moves a stuck plan onto the doctor's current tier keeping the approved features, price and dates. The **monthly appointment limit** is part of a custom plan (`doctor_custom_plans.monthly_appointments_limit`, `20261029170000_custom_plan_appointment_limit.sql`): NULL = the tier's standard limit (`platform_settings.basic_appointment_cap`), -1 = unlimited, n = n per month; it is a number, not a `features` row, and only Pro-based plans carry one (Premium and trial are unlimited). `doctor_monthly_appointment_limit()` is the single place that decides it (Premium/trial, then an *applying* custom plan, then the standard); the booking trigger, `get_appointment_cap_usage` and the warnings all read it. On approval `review_plan_request(..., _appointments_limit)` reads NULL as "keep the plan's current limit", 0 as "reset to standard", -1 unlimited, n a number, so a features-only approval can never wipe a limit. The limit is judged for *today's* plan when a booking is made, not for the booked month. Plan cards show the STANDARD limit (`standardCap`); a custom limit appears as the custom plan's own line. In the approve dialog **Starts/Ends** are the dates the custom price and features apply; they are separate from the doctor's **paid until** (`plan_end`). Leave Ends blank or set it after the next renewal, because the price is read at payment time. Dates shown to users are formatted in IST (`src/lib/istDate.ts`); plan/trial days left come from `summarizePlan()` (`src/lib/planSummary.ts`), used by the header chip (`PlanStatusChip`) and dashboard `PlanCard`.

**Social media marketing add-on** (`20261127180000_social_marketing_addon.sql`, spec `docs/superpowers/specs/2026-11-27-social-media-marketing-addon-design.md`): a service the team delivers, so the app only *records* it. One row per clinic in `custom_plan_social_marketing` (FK to `doctor_custom_plans`), status `draft` -> `active` -> `ended`, written only by `save_social_marketing_scope` / `activate_social_marketing` / `end_social_marketing` (`plan_requests.manage`; clients have no write policy). **`social_marketing_missing()` is the single activation gate** (platforms, posts + types, who publishes, reporting, approval process, fee, ad spend when paid ads, account access, client agreement with date + reference); `missingForActivation()` in `src/lib/socialMarketing.ts` mirrors it by hand. Changing the scope of an active record, or re-scoping an ended one, drops it to draft and clears the agreement. It ends with its custom plan (trigger on `doctor_custom_plans.status`). **Doctors can ask for it** from Customize my plan (`plan_requests.requested_social_marketing`, `submit_plan_request(..., _social_marketing)`, `20261128100000`): the flag is only a request, it is not a `features` row, and it creates nothing; the review dialog pre-ticks the switch and the superadmin still agrees the scope before activation. The doctor cannot ask while the add-on is active. RLS: superadmin reviewers read everything; the clinic reads its own row only while `active` on a live plan (never a draft). The fee is billed outside the app and is deliberately NOT part of `monthly_price` or any Razorpay order. UI: `SocialMarketingDialog` (Plan Requests > Active plans), a switch in the approve dialog (creates an empty draft), and the read-only `SocialMarketingCard` in `CustomPlanSection`. DB checks: `supabase/tests/social_marketing.sql`.

### Doctor discovery & SEO

Full plan in `docs/doctor-discovery-plan.md`. The app is a client-rendered SPA, so crawlers and link previews would only see the generic `index.html`. `vercel.json` rewrites `/dr/:slug` and `/doctors[/:city[/:specialty]]` to the Vercel Edge function `api/seo.ts` (logic in `src/lib/seo/handleSeoRequest.ts`), which injects page-specific head tags, JSON-LD and crawlable body into the built `index.html`, and falls back to the plain shell on any upstream failure. `DoctorPublicPage` and the Edge function share `src/lib/seo/doctorSeo.ts`.

- Files under `src/lib/seo/` and `src/lib/directory/` are bundled by Vercel: **use relative imports only (no `@/`)**.
- **Keep `api/seo.ts` and `api/sitemap.ts` pinned to `regions: ["syd1"]`** (next to the Supabase project). Each uncached render makes several round trips to Supabase; from the default region that was 0.7-1.9s, which Google counts against crawling ("Discovered - currently not indexed"). Pages are cached `s-maxage=3600` + `stale-while-revalidate=604800` (`SITE_CACHE`), so a crawler almost always gets the warm copy. If Supabase moves region, move these with it. Static marketing pages (`kind=page`, `staticPages.ts`) get their own title/canonical; `/auth` is `noindex` and filtered out of the sitemap by `proxySitemap`.
- `src/lib/directory/slug.ts` must stay byte-identical to `supabase/functions/_shared/directorySlug.ts` (a test enforces it) and match SQL `directory_slugify()` in the `doctor_directory` migration.
- Directory search runs through the `search_doctors` / `directory_facets` SECURITY DEFINER RPCs (safe columns only); `profiles.directory_listed` is the doctor's opt-out. Hubs with fewer than `DIRECTORY_MIN_INDEXABLE` doctors are `noindex` and left out of the sitemap.
- **Health Articles hub** (`/health-articles[/:category]`): an index over doctors' published `blog_posts`, never a copy - each article's canonical URL stays `/dr/:slug/blog/:post`. Reads go through `search_blog_posts` / `blog_facets` (SECURITY DEFINER; they apply the doctor-level filters RLS does not: onboarded, slug, not `cancelled`, `directory_listed`). Rendered for crawlers by `api/seo.ts` (`kind=articles`, logic in `src/lib/seo/healthArticlesSeo.ts`, relative imports only). `blog_posts.hub_hidden` is a superadmin-only moderation flag (guard trigger `guard_blog_hub_hidden`; owner or `moderation.manage`), separate from `is_published`. `published_at` is the original publish date: edits must keep it (`src/lib/blogPublish.ts`). Topic hubs with fewer than `DIRECTORY_MIN_INDEXABLE` posts are `noindex` and not in the sitemap. New public RPCs must be added to `INTENDED_ANON` in `tests/db/schemaAudit.test.ts`.
- **Article pages for crawlers:** GPTBot, ClaudeBot and PerplexityBot do not run JavaScript, so the Edge HTML for an article carries the whole article via `renderArticleBody` (`src/lib/seo/articleHtml.ts`, an allowlist tokenizer, no DOM) - never reduce it to a text blob. Article JSON-LD authors are `Person` with a bare name plus `honorificPrefix` (Google rejects honorifics in `author.name`). Do not add `FAQPage` (Google removed FAQ rich results in May 2026) or `lastReviewed` (`updated_at` also moves on moderation toggles). `blog_posts.ai_assisted` is set when a doctor uses the AI Blog Writer and drives the on-page AI disclosure.

### Styling

Tailwind theme colors are CSS custom properties (HSL) defined in `src/index.css` and mapped in `tailwind.config.ts` — brand tokens are `royal`, `teal`, `navy`, `spark`, `ai-purple`, plus semantic `success`/`warning`/`destructive`. Dark mode uses the `class` strategy. Headings use the `font-heading` (Plus Jakarta Sans) family, body/dashboard text uses `font-body`/default (Inter). shadcn/ui components (`src/components/ui/*`) are generated via `components.json` (style: default, no RSC) — treat them as customizable local code, not a vendored package.

**Theme model (one global palette, derived from the logo — navy wordmark, blue→cyan "D", lime nodes).** Token values live only in `:root` and `.dark` in `src/index.css`; there is no per-surface theme override. `--primary`/`--royal` is a deep royal blue (white on it ≈ 7.7:1), `--accent` is shadcn's pale hover surface (not a brand color — use `teal` for the cyan brand hue), and `--navy` is the ink/wordmark color. Bright hues (`teal`, `spark`, `success`, `warning`, `destructive`) are **fills** (`bg-*`, borders); `tailwind.config.ts` `textColor` deliberately maps `text-teal/spark/success/warning/destructive` to darker "ink" tokens (`--teal-ink`, …) that pass 4.5:1 on light surfaces and flip lighter in `.dark`. On a **dark surface** (`bg-primary`, `bg-navy`, gradients) use `text-teal-bright` / `text-spark-bright` or white instead. `.gradient-brand` is the logo gradient. Shared admin pieces: `components/admin/StatusBadge` (appointment status → color; don't re-declare status color maps) and `components/admin/StatCard` (distinct from the gradient `components/shared/StatCard`). Fonts (Inter, Plus Jakarta Sans, Caveat) are self-hosted in `public/fonts` — the CSP in `vercel.json` blocks Google Fonts, so don't add them back.

**Doctor public site exception (`/dr/:slug`).** The doctor site has its own scoped design layer ("Editorial Warmth"): tokens live in `src/styles/doctor-site.css` under `.doctor-site` / `.dark .doctor-site` and are exposed as Tailwind `ds-*` utilities (colors, `font-ds-display` = self-hosted Newsreader, `text-ds-*` sizes, `ease-ds-*`, `shadow-ds-*`, `rounded-ds-*`). It does not use the global palette above, and nothing outside the doctor site reads `ds-*`. Merge classes there with `dsCn` (`src/components/doctor/ui/dsCn.ts`), not `cn`. Portalled overlays (dialogs, drawers) must carry the `doctor-site` class themselves. Its responsive rule also differs from the marketing convention below: single column under 640px (17px minimum body text for elderly/low-vision patients), side-by-side from 768/1024px. Motion: `framer-motion` for UI (do not import `motion/react`: it ships a second copy of the runtime), GSAP (+SplitText/ScrollTrigger) and Lenis only as lazy chunks via `src/components/doctor/motion/gsap.ts` `loadGsap()` / `SmoothScroll` (never import `gsap` or `lenis` statically here), Lenis for smooth scroll on this page only. Visual effects live in `src/components/doctor/effects/` (glass `ds-glass`, dot grid, cursor spotlight `useSpotlight`, `CountUp`), ported from Magic UI / Aceternity patterns; they animate transform/opacity only, are mouse-only where interactive, and stop for reduced motion. Per design review the hero photo and all buttons are deliberately static (no tilt, parallax, magnetic pull or press scale) and there are no colour-gradient backgrounds: don't add them back. No WebGL/3D on this page: a decorative R3F accent behind the hero portrait measurably dropped scroll frames (29 over 33 ms vs 0 without it, 4x CPU) and was removed. Spec: `docs/superpowers/specs/2026-11-24-doctor-site-redesign-design.md`.

Responsive design convention in this codebase: admin/superadmin data tables render as an actual `<table>` inside `<Card className="hidden md:block">` alongside a parallel `<div className="md:hidden space-y-2">` of `<Card>` rows for mobile, rather than trying to make one table layout serve both. Marketing/profile pages that pair a text block with an image, form, or accordion keep them side-by-side at every width (not stacked) by making the grid unconditional (`grid-cols-N` with no breakpoint prefix) and scaling text/icon/image sizes down at the base and up through `sm:`/`md:`/`lg:`, rather than reflowing to a single column on narrow viewports.
